# Managed credential storage

Native sub2api persistence supplies the [managed verifier](README.md#managed-database-agent-token-authentication) and the original Runner credential management lifecycle. The existing default-off `webcodex_runner.enabled` setting gates polling and management together; normal configuration validation requires six positive registry/transport limits, including the separate `max_jobs_per_runner` retention budget.

## Storage decision and source map

All WebCodex source references use frozen revision `97ad66949a859174911c2f6da2ff1063be98bfa9`. The original `api_keys` definition is in `crates/webcodex-store/src/schema.rs:89-105`, its record in `models.rs:234-263`, and its lifecycle methods in `accounts.rs`.

The native [repository](../../repository/webcodex_api_key_repo.go) uses the existing `*sql.DB` pool, following host SQL repository practice. The [embedded migration](../../../migrations/238_webcodex_api_keys.sql) creates only `wc_api_keys`, a namespaced version of the original managed credential table. The normal host migration runner discovers it through `migrations.FS`; no alternate migration runner or Ent-generated schema is introduced. Host `api_keys` requires a plaintext `key` and integer credential ID and lacks the original kind/scope/client binding. Inventing model keys to carry hash-only credentials would change their authority and lifecycle.

| Original field | Storage and projection |
|---|---|
| `id` | Original TEXT credential ID, distinct from host model APIKey ID |
| `user_id` | BIGINT foreign key to existing `users(id)`, without cascade deletion; the sole original field whose identity representation changes |
| `name`, `key_hash`, `key_prefix` | Original TEXT values, hash UNIQUE; no plaintext token column |
| `created_at` | Signed BIGINT Unix seconds, required |
| `last_used_at`, `revoked_at`, `expires_at` | Nullable signed BIGINT Unix seconds; zero and negative values remain distinct from null |
| `scopes` | Original TEXT, default empty; order, duplicates and unknown values remain unchanged |
| `kind` | Original TEXT, default `user`; explicitly inserted empty/unknown values are preserved for verifier classification/rejection |
| `allowed_client_id` | Original nullable TEXT binding |

The unique hash index already supports lookup; the original user index is retained. No second user/login, model group, tenant, or authority table is introduced. Physical `user_id` is supplied only after trusted host selection or explicit legacy ID mapping. `GetByHash` converts it with `runner.HostUserOwner` to the verifier's existing string `sub2api_user_<positive int64>`; no verifier API changes are needed. Imported owner/subject/fingerprint references still require explicit consistent rewriting. No automatic import, username matching or account creation occurs.

## Lifecycle and host adapter

- `Insert` retains all twelve supplied fields (`accounts.rs:63-83`), uses a plain INSERT (no conflict revival), and requires a nonempty credential ID and positive host ID. It is a trusted persistence operation, not token issuance or public import authorization.
- `GetByID` includes revoked rows for management (`accounts.rs:290-302`).
- `GetByHash` queries the exact supplied hash and excludes every non-null revocation marker (`accounts.rs:49-60`). Expiry and current host status remain verifier checks. Each lookup creates an owned snapshot and performs a fresh database query.
- `Revoke` uses original `COALESCE(revoked_at, timestamp)` first-revocation semantics (`accounts.rs:306-313`). PostgreSQL `UPDATE ... RETURNING` makes the original update/read a single statement. Missing IDs return `(nil, nil)`.
- `UpdateLastUsed` updates only the original column, with missing IDs succeeding as a no-op (`accounts.rs:352-358`). The verifier treats failure as best effort; this never clears revocation or changes scopes.

[NewWebCodexHostUserResolver](../../repository/webcodex_host_user.go) calls existing `service.UserRepository.GetByID` for every authentication. It requires matching ID, active status and `DeletedAt == nil`, even if a context bypasses Ent soft deletion. Profile names, admin roles, balance and model groups grant no Runner rights. Missing users fail closed, dependency errors are sanitized, and cancellation yields no principal.

Construction is explicit: pass `NewWebCodexAPIKeyRepository(sqlDB)` and `NewWebCodexHostUserResolver(userRepository)` to `runner.NewAgentTokenAuthenticator` along with its required options. These are actual host types; no pool is opened by the constructor. Repository methods use individual SQL statements and do not join an outer Ent transaction. Future multi-record import/issuance must add explicit transaction composition before claiming atomic owner/grant rewrites. Auth lookup, user lookup and last-used touch are not one atomic transaction against concurrent revocation; already admitted in-flight work is not retroactively cancelled.

## Host-authorized management routes

[SetupRouter](../../server/router.go) supplies the real host middleware chain to the [management mount](../../server/webcodex_agent_tokens.go): `JWTAuthMiddleware → BackendModeUserGuard → panelRateLimiter.Global() → AuditLogMiddleware`. `registerRoutes` passes the same panel limiter instance used by host user management; counters stay in its existing per-user global bucket, including its configured admin exemption and Redis failure policy. JWT middleware loads the current repository role before the guard and limiter evaluate any admin exemption. Backend mode denies non-admin self-service. These four original POST paths stay outside `/api/v1`, GPT Actions/OpenAPI and model tools; that path compatibility does not exempt them from host panel policy. Polling still mounts separately outside these panel guards. Missing or invalid panel JWTs receive the host middleware's 401 error envelope; backend mode and throttling keep the existing host 403/429 envelopes. Runner credentials, model API keys, legacy bootstrap/account/PAT/OAuth credentials and admin API keys cannot use these routes. `AdminAuthMiddleware` is deliberately not used because that host middleware can admit non-JWT admin credentials. Authenticated handler errors retain the original `{status,error}` envelope, with fixed messages for parser/database failures that could contain secrets.

The actual `jwt_auth.go` admits only an Authorization header with the Bearer scheme; it never reads cookies, query parameters or form fields for a JWT. Cookie-only browser requests cannot manage credentials, so this slice adds no cookie authentication or cookie-based CSRF admission. Host `RequestLogger`/`Logger` record path, timing and status, not request/response bodies or raw Authorization. JWT failures use fixed error messages rather than validator error strings. Session-binding mismatch audit uses actor/session-request metadata, not the bearer. The existing `auditBodyOmittedRoutes` explicitly omits the entire request body for all four management POST routes, including arbitrary names and unknown fields that could hide secrets; audit does not pre-read these bodies and does not capture response bodies. Admitted requests retain host action/actor/status and request metadata with a masked header credential. Backend-mode/rate-limit rejections precede audit exactly as in host user management. The management handler never attaches private errors to Gin's logged error list. `Cache-Control: no-store` is installed before JWT, including authentication/policy failures and the one-time plaintext creation response.

The original catalog (`src/route_metadata/account.rs:90-128`) requires `account:manage`, then `runner_tokens_http.rs:48-75` checks admin/self. This native slice maps that account-management authority to an authenticated full host panel JWT, matching existing host account administration. It does not add `account:manage` to a JWT or mistake the host role for a scoped WebCodex PAT. Supporting original scoped PAT/account/OAuth entry later requires their independent validators. The existing JWT middleware verifies signature, expiry, token version, session binding and current active User. Management reads the current User repository again and requires matching immutable ID, active state and no deletion; admin/self uses the current repository role, never a stale JWT role claim.

The request field `username` remains unchanged but must contain `sub2api_user_<positive int64>` (trimmed, canonical decimal, no leading zeros). Both response `username` and `user_id` are JSON strings carrying that canonical owner; the physical `wc_api_keys.user_id` column remains the existing host User's bigint foreign key. Mutable usernames are not accepted as target aliases. A non-admin may select only its own ID; a current admin may select another existing host User. Create/register reject a disabled target. As in the original routes, an active admin can list/revoke a disabled target for recovery; deleted targets are not available. Caller disable/deletion always refuses management.

| Original POST path | Request | Success response |
|---|---|---|
| `/api/agent-tokens/create` | required `username,client_id`; optional nullable `name,scopes,expires_at` | `success,token,token_prefix,token_id,name,kind,username,user_id,allowed_client_id,scopes,created_at,expires_at` |
| `/api/agent-tokens/register_hash` | required `username,client_id,token_hash,token_prefix`; optional nullable `name,expires_at`; omitted/empty `scopes` default | `success,token:{id,name,token_prefix,allowed_client_id,scopes,created_at,expires_at}` |
| `/api/agent-tokens/list` | required `username` | `success,username,user_id,tokens,count` |
| `/api/agent-tokens/revoke` | required `username,token_id` | `success,token` |

Every success is 200. List/revoke token metadata is exactly `id,user_id,name,token_prefix,kind,allowed_client_id,scopes,created_at,last_used_at,expires_at,revoked_at` (`src/runner_tokens_http/responses.rs`). It contains no hash or plaintext. Lists include revoked/expired agent rows, ordered by `created_at DESC`, at most 200. The SQL query enforces the original post-query limit before loading records. Safe management reads and revoke RETURNING select only those eleven storage metadata columns, excluding `key_hash`.

Validation follows `src/runner_tokens_http/routes.rs` and `src/auth/pat.rs`: trimmed client ID is 1–80 ASCII letters/digits/`-_.`; name trims, falls back to `default` for create or client ID for registration, and permits at most 128 Unicode scalar values. Future nullable expiry remains signed int64 Unix seconds. Scope input trims, skips blanks and deduplicates in first-seen order; only `agent:register`, `agent:poll`, `agent:result`, `agent:job_update` are accepted. Create omitted/null scopes grant those four, but explicit `[]` grants none. Register omitted/`[]` grants all four, explicit null is invalid, and `[" "]` normalizes to no scopes rather than defaulting. Keeping job_update does not add a Job route. The [DTOs](../protocol/agent_tokens.go) preserve original required/null/unknown-field and duplicate-known-field behavior through the existing serde-compatible JSON decoder, including Unicode and int64 fidelity. Only register_hash rejects unknown fields; it never accepts a plaintext token field.

Create uses maintained Go crypto randomness for `wc_agent_` plus 64 lowercase hex characters and a separate UUID v4 record ID; its 16-character display prefix and SHA-256 hash are stored. Plaintext is returned only after the INSERT succeeds and is never persisted or logged. There is no recovery/replay of that plaintext after a lost response; another create is another credential. Hash registration accepts a bare 64-hex or `sha256:<64hex>` hash and normalizes it to lowercase. Its trimmed display prefix must start `wc_agent_`, contain only ASCII letters/digits/underscore and have length 10–32; the server cannot verify this display prefix against unknown plaintext. Each inserts one original row with `kind=agent` and a required client binding. PostgreSQL uniqueness conflicts during register_hash return 409, with no upsert, retry or revival of revoked rows.

Revoke is one `UPDATE ... WHERE id AND user_id AND kind='agent' RETURNING ...`, preserving the first timestamp with COALESCE. There is no get-then-unscoped mutation. When it finds no matching row, a separate owner/kind-only diagnostic read retains the original 403 foreign-owner, 400 non-agent and 404 missing distinction; a concurrently changed matching row instead returns 409. That read cannot cause another write. Existing list/revoke source methods are in `crates/webcodex-store/src/accounts.rs:276-313`; native scoped SQL is in [webcodex_agent_tokens.go](../../repository/webcodex_agent_tokens.go).

Management reuses the explicitly configured `WebCodexRunner.MaxBodyBytes` (`webcodex_runner.max_body_bytes`) as its complete-body limit through MaxBytesReader, returning 413 for excess even on unknown-length bodies. Enabled configuration already validates that this operational bound is positive; no second undocumented management limit or new configuration key is introduced. Global CORS may answer OPTIONS with 204 without authenticating or enabling the route. Disabled configuration mounts none of these paths.

The source register_hash additionally checks `get_account_credential_by_hash` for active account-credential collisions (`routes.rs:365-377`). Native account credentials and their table/verifier have not been migrated. This check has no native target in this slice: the unique `wc_api_keys.key_hash` covers all currently persisted native managed kinds, including revoked rows, but not a future separate account-credential table. Original account-credential migration must restore cross-family collision handling before enabling that credential family. Model API keys are not substitutes for that table and are not queried or granted management authority.

Each operation changes at most one credential row, as in these original management routes; no owner/grant/multi-record write or transaction is introduced. User authorization reads are not atomic with inserts/revokes against concurrent disable/role change, and an admitted request is not cancelled retroactively. Multi-record import/pairing or other credential families still require their original transactional semantics and explicit host transaction composition.

## Offline validation and remaining integration

`go test -race -count=1 ./internal/repository -run '^TestWebCodex'` uses SQLmock with fabricated records. Tests cover original column values and int64/null fidelity, exact query arguments, canonical projection, absent/revoked rows, first-revocation SQL, isolated last-used writes, scan/query errors, cancelled contexts, nil dependencies, current user disable/deletion/mismatch, sanitized errors, and full repository-to-verifier fixtures with exact UTF-8 token hashing and all stored scopes. The host adapter test runs real `NewUserRepository` and Ent queries over SQLmock. `go test ./migrations -run '^TestWebCodex'` checks the embedded DDL field/FK/index contract structurally.

`go test -tags unit -race -count=1 ./internal/server ./internal/server/middleware ./internal/repository ./internal/webcodex/protocol -run '^Test(WebCodex|AgentTokenManagement)'` covers actual Gin-mounted management with fabricated signed JWTs through `NewJWTAuthMiddleware`, backend mode with current-role admin checks, shared per-user panel throttling using a Redis command hook with no network, actual audit service flushing to an in-memory capture repository, Cookie/query/form-only refusal and no-store headers, whole-body audit omission across all four paths and success/error statuses, real credential SQL over SQLmock, create-to-actual-verifier authorization, exact registration metadata/scopes/nulls, no secrets in list/revoke/error/audit records, canonical admin/self and current user checks, disabled-target recovery, duplicate hash rejection without revival, user/kind-scoped revoke, configured body limits (including above 64 KiB and unknown-length requests) and default-off/CORS behavior. Repository tests also check NULL/int64 fidelity, safe metadata selection, bounded listing, cancellation and row errors. These commands use only fabricated credentials and owned fixtures.

No real PostgreSQL DDL, foreign-key/unique enforcement or concurrent database transaction behavior is claimed by SQLmock. The migration has not been applied to a database. Original account/PAT/OAuth/bootstrap credential families, cross-family account-hash collision checks, import, UI, persistent registry/results and full G2 dispatch remain later work. The default-off application integration receives the host SQL pool/User repository and real host JWT middleware; it mounts the four original polling routes and four management POST routes, and closes the in-memory registry during HTTP shutdown. Applying the normal migration creates an empty credential table and seeds no credential.
