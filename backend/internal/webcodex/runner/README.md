# Runner polling registry

This reference describes the synchronous polling portion of the WebCodex Server migration. Its original wire DTOs are owned by [protocol](../protocol/README.md). The package is not mounted by sub2api's router and does not execute commands.

## Admission and ownership

`NewHTTPHandler` requires a host authenticator and a positive complete-body byte limit. The authenticator returns the verified credential kind, owner, bound `client_id`, scopes and original shared-key/project-grant access projection. It must check expiry, revocation and credential authenticity. A model API key or an unverified JSON identity does not grant Runner access.

| Original route (POST) | Original required scope |
|---|---|
| `/api/shell/agent/register` | `agent:register` |
| `/api/shell/agent/poll` | `agent:poll` |
| `/api/shell/agent/result` | `agent:result` |
| `/api/shell/agent/offline` | `agent:register` |

Agent tokens are bound to `client_id` and owner. Shared keys are isolated by the verified SHA-256 group; their requested owner is not an authorization input. Bootstrap is an explicit host-auth kind. Global visibility alone does not bypass managed-Runner ownership for dispatch. Query credentials and duplicate Authorization headers are rejected. Credential-verifier errors are never reflected in responses.

Registration requires generation 2 and all 22 original baseline capability bits. These bits are facts reported by a real executor, not defaults inferred from the generation. A partial DSH executor cannot register merely by supporting the six migrated direct request codecs. Same-instance reconnect preserves queued and dispatched work. A new instance retires the prior instance, settles prior requests with their dispatch evidence, and never transfers those requests to the replacement. The original bounded retirement history is 16 instances.

## Managed database agent-token authentication

`NewAgentTokenAuthenticator(repository, resolveHostUser, options)` returns the existing `Authenticate` callback accepted by `NewHTTPHandler`. It reads managed credentials through `AgentCredentialRepository.GetByHash`, resolves the existing host User by immutable positive ID on every call, and updates the original credential's `last_used_at` on a best-effort basis. It mounts no application route, connects to no database, starts no worker and caches no authentication result. Supply concurrency-safe dependencies and an explicit clock and positive `MaxTokenBytes`.

The repository returns an owned `AgentCredentialRecord` snapshot. This is the authentication projection of the original `api_keys` columns: `id`, `user_id`, `key_hash`, `kind`, `scopes`, `allowed_client_id`, `expires_at`, `revoked_at`. Lifecycle metadata (`name`, `key_prefix`, `created_at`, `last_used_at`) is retained by the native repository described in [managed credential storage](CREDENTIAL_STORAGE.md); the verifier does not replace that record or the key lifecycle. `UserID` remains a string reference, normalized at the repository/import boundary to the canonical host subject returned by `HostUserOwner`. The verifier strictly parses its positive int64 ID and rejects unconverted legacy IDs, profile names, leading zeros and other noncanonical representations. Original nullable Unix-second expiry/revocation values remain nullable integers. A returned row must match the computed lowercase SHA-256 hash and have no revocation marker. Raw database `kind="agent"` requires a valid client binding and maps to `Principal.Kind="agent_token"`. Original `user` and legacy empty kinds undergo the same credential/user/expiry checks but map to non-transport `api_token`, preserving the registry's 403. Unknown kinds are rejected and never upgraded to agents. All stored scopes are projected; exact requested-scope authorization belongs to the registry.

`HostUserOwner(id)` defines the new-record owner representation as `sub2api_user_` followed by the positive host ID in base-10 (no leading zeros). The maximum positive int64 produces a 32-character owner, within the original 64-character lowercase ASCII username alphabet. This helper is available to trusted dispatchers as well as authentication; changing its encoding requires migrating stored owners. `HostUserResolver` receives only that ID and must return the same ID with `Active=true` only if the current host user exists, is not deleted and has active status. It must not select a user by profile username or authorize from a stale snapshot. Nickname, role and model billing group are not inputs. An admin profile still produces an ordinary agent principal, with no bootstrap or group bypass.

This deterministic representation applies to **new records**, as permitted by `SUB2API_DSH_SYSTEM_ARCHITECTURE.zh-CN.md:173`. Existing WebCodex imports require an explicit old-user-ID to host-user-ID mapping and consistent owner/subject/authority-reference rewrites before admission. The verifier performs neither import nor rewriting and does not promise compatibility with an old client still submitting its original username as owner. New registrations may omit owner, allowing the registry to fill the verified value, or supply exactly `HostUserOwner(id)`. Username similarity never selects or merges users. Host User IDs must remain immutable and must not be reassigned to another person.

Managed records cannot carry `ProjectGrantID` or `SharedKeyHash`. Original `ProjectAgentTokenVerifier` is a separate configuration-backed verifier and is not implemented here; a project agent credential must never be represented as a managed database row. OAuth, shared keys, account credentials, bootstrap and open mode are outside this constructor. Original user/empty kinds are recognized only as verified non-transport identities, not as Runner agents. There is no verifier-chain fallback or auth-disabled mode. All stored scopes survive projection, including the original `agent:job_update`, future/unknown scopes and `admin`; scope order and duplicates are preserved. The verifier does not repeat issuance-time scope validation. Neither extra scopes nor `admin` turn a principal into bootstrap, satisfy a missing exact transport scope or bypass owner/client checks. Retaining `agent:job_update` does not add a Job endpoint. Empty scopes authenticate but grant no transport operation.

### Source contracts and deliberate host boundaries

All WebCodex references below refer to frozen revision `97ad66949a859174911c2f6da2ff1063be98bfa9`.

| Contract | Original source and implementation boundary |
|---|---|
| Exact token bytes and hash | `src/auth/pat.rs:18-31`: SHA-256 of UTF-8 bytes, lowercase hex, no trim. The DB verifier at `src/auth/tokens.rs:76-79` looks up by hash rather than trusting the prefix. This implementation accepts valid UTF-8 within the explicit host byte limit. The generated `wc_agent_` plus 64-hex format (`pat.rs:47-59`) is not a universal DB-verification length requirement. `MaxTokenBytes` is a configured operational bound, not an invented source protocol constant. |
| Not found and errors | `crates/webcodex-store/src/accounts.rs:49-60` returns no row for missing/revoked hashes. `src/auth/tokens.rs:79` originally uses `if let Ok(Some(...))`, so an API-key query error can fall through to account lookup; the chain at `tokens.rs:352-379` distinguishes unrecognized from invalid credentials. This managed api_keys verifier fails closed on every repository/resolver error, with a fixed unavailable error and no fallback. It never wraps sensitive dependency error text. `(nil, nil)` means not found; invalid credentials and unknown kinds return a fixed invalid error. The existing HTTP handler returns its generic 401 for either error. Verified original `user`/empty kinds instead reach the registry as non-transport `api_token` and receive 403; this does not add PAT management or other credential verifier families. |
| Revocation and expiry | `accounts.rs:54` excludes every non-null `revoked_at`; `models.rs:295-302` considers any marker revoked and expiry reached at `now >= expires_at`, in Unix seconds. No future-dated revocation marker is ignored. The clock is read after host resolution; no balance, subscription or quota check substitutes for expiry. |
| Kind and scopes | `models.rs:305-316` defaults empty kind to `user`, and only raw `agent` is an agent. `src/auth/tokens.rs:99-113` classifies the verified row and projects `scopes_vec`; `models.rs:290-292` splits stored whitespace without deduplicating, despite its comment. `src/auth/scopes.rs:43-62` and the four `AGENT_SCOPES` at `crates/webcodex-core/src/authority.rs:102-107` constrain issuance, not per-request verification. Every stored scope is retained here, including future/unknown strings and `admin`. Registry requires the exact operation scope and the proper principal kind; extra values cannot broaden that authority. Go `strings.Fields` preserves the source whitespace behavior: U+0085 separates scopes; U+FEFF stays inside the scope string and cannot make that string match a known scope. |
| Client and owner bounds | `src/auth/pat.rs:147-167` admits normalized client IDs of 1-80 ASCII letters/digits/`-_.`; malformed stored values are rejected, not trimmed into another binding. `pat.rs:170-193` defines the 1-64 lowercase ASCII letters/digits/`_-` owner alphabet. The resolver uses immutable host ID; the existing registry enforces the exact owner/client equality. |
| Parent authority and project grants | `src/auth/project_credential.rs:19-24,84-96` defines the separate project agent verifier. OAuth checks include non-revoked owning client (`src/auth/tokens.rs:229-238`), project grant ownership (`tokens.rs:301-323`) and the currently active project-share subject/session (`src/auth/project_share.rs:50-63`). These are distinct from a managed api_keys row. No grant/ancestor validation is claimed here: project-derived credentials are outside the repository contract and cannot be projected into a grant group. |
| User and last-used | `src/auth/tokens.rs:80-114` checks the owning user, then expiry, and treats `last_used_at` failure as best effort. The host resolver must enforce active/not-deleted against the requested ID. Cancellation before or during dependencies returns no principal, including cancellation during the last-used write. Dependency calls use the request context; their implementations must honor deadlines. No private error is logged and no retry goroutine is started. |

The repository and user resolver remain trusted host adapters: they must return authoritative snapshots, apply explicit import mapping and exclude project-derived records. This package cannot make independently queried data transactionally atomic against a concurrent revoke, or stop a call in a dependency that ignores its context. It revalidates on every request and retains no positive authorization cache; in-flight work remains subject to the existing registry's dispatch-evidence rules. This feature neither cancels already-dispatched work nor implements a revocation broadcast.

Future application mounting must be explicitly enabled (proposed `webcodex.runner.enabled=false` by default). Disabled configuration must not construct the registry or register routes. Enabling requires a real credential repository, current host-user resolver and positive registry/body/token bounds, with registry `Close` in application cleanup. The native repository, migration and current host-user adapter are implemented as described in [managed credential storage](CREDENTIAL_STORAGE.md). The flag and Wire/router mounting are **not implemented**; actual app routes remain absent. Preserve the original root `/api/shell/agent/...` paths rather than `/api/v1`, and keep model APIKey middleware out of the Runner credential path.

## Synchronous requests and lifecycle

Trusted host callers use `Enqueue` only after establishing the original project and operation scopes. The HTTP adapter has no dispatch endpoint. The caller supplies the durable unique `request_id`; this memory registry does not replace the Connector execution record or idempotency transaction.

The current dispatch decoder accepts `run_shell`, `run_process`, `run_script`, `file_read`, `file_write` and `file_list`. Each request must match the target's advertised capability. Job-backed operations and deferred families fail explicitly. Structured argv/script payloads remain structured and are not concatenated into shell commands. A request is delivered at most once while pending, including after a polling response is lost. Consuming a result requires its exact dispatched request, client and active instance. A duplicate consumed/expired result receives the original HTTP 400 failure behavior; success means an in-memory waiter accepted it, not a durable acknowledgement.

Each returned `Pending` must be awaited with a bounded context or explicitly cancelled. Cancellation before dispatch removes the queue item. After dispatch, `Outcome.Dispatched` stays true even when the waiter fails, so timeout, disconnect and replacement cannot prove that execution never started. Cancellation does not stop a remote process and cannot authorize automatic retry. `Close` synchronously settles all waiters; the registry owns no subprocesses, sockets or timer goroutines.

Runner views preserve `online`/`stale`, second-based timestamps, and `pending_requests` as the undelivered queue length. Result stdout/stderr preserve the original last-256-KiB UTF-8 tail and truncation notice. The notice is additional to the per-stream limit; the complete HTTP body has a separate configured bound. Registry options bound retained nodes and pending requests. Original shared-key per-group/global ceilings remain 16/1024. Cancelled queue items are removed immediately. Offline records are retained until registry disposal; TTL collection is deferred.

## Validation

Run from the backend directory:

```sh
go test -race ./internal/webcodex/...
DSH_RUNNER_CHECKOUT=/absolute/path/to/deepseek-harness go test -run TestDSH -v ./internal/webcodex/runner
```

Focused credential coverage uses only memory fixtures:

```sh
GOPROXY=off GOSUMDB=off GOTOOLCHAIN=local CGO_ENABLED=1 \
  go test -race -count=1 -run '^TestAgentCredential' ./internal/webcodex/runner
```

The full local runner/protocol race suite also exercises the existing loopback fixtures and needs no external service. The `TestAgentCredential*` tests cover the public SHA-256 vector/exact bytes, explicit dependencies and byte bounds, malformed rows/kinds, canonical string user references, source client limits, complete stored scope projection and whitespace, expiry equality, active same-ID host user, profile-independent owner, sanitized lookup errors, best-effort touch, cancellation and concurrent fresh checks. Memory-only HTTP tests use the real verifier with fake repositories and fabricated results to cover the four polling routes, revocation/deletion/user disable after registration, exact scope/client/owner rejection without lease or pending-result mutation, user/legacy-kind transport 403, mixed known/future scopes, admin without bootstrap, body/header credential boundaries and unchanged G2 admission. No test token is a deployed credential. These tests do not validate a real repository, migration, executor or application route mount.

The opt-in cross-language tests launch the test-only DSH stdin driver through `node --import tsx/esm`. They need DSH's workspace dependencies. They round-trip direct request JSON, including signed/unsigned 64-bit extrema, and prove that the actual partial DSH client is rejected by the Go generation check before executor invocation. Go loopback tests use a fixture credential verifier and fabricated results; they do not prove local execution or end-to-end ChatGPT Connector operation.

## Migration limitations

The native managed-credential verifier now has a host SQL credential repository, embedded migration and current User repository adapter; see [storage integration](CREDENTIAL_STORAGE.md) for the original field map and offline SQL fixture checks. Router/composition mounting remains absent. WebSocket/QUIC, provider policy sanitization, paged project inventories, Jobs/recovery, Generic ToolRuntime, ProjectConnector/OAuth/MCP and UI are not implemented here. Registration carrying policy/provider/recovery inventory is explicitly rejected until those owned semantics are migrated. A database, transaction and outbox are required before claiming persistent result receipt, restart recovery or durable idempotency. A full generation-2 DSH execution provider with its real non-Agent guard/approval/filesystem/sandbox owner remains required. No package option disables that generation check.
