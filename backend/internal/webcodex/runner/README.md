# Runner polling registry

This reference describes synchronous polling, legacy structured process Jobs and opt-in same-Server/same-instance sequenced reconciliation in the WebCodex Server migration. Its original wire DTOs are owned by [protocol](../protocol/README.md). The package is mounted by sub2api's router only when explicitly enabled and does not execute commands.

## Admission and ownership

`NewHTTPHandler` requires a host authenticator and a positive complete-body byte limit. The authenticator returns the verified credential kind, owner, bound `client_id`, scopes and original shared-key/project-grant access projection. It must check expiry, revocation and credential authenticity. A model API key or an unverified JSON identity does not grant Runner access.

| Original route (POST) | Original required scope |
|---|---|
| `/api/shell/agent/register` | `agent:register` |
| `/api/shell/agent/poll` | `agent:poll` |
| `/api/shell/agent/result` | `agent:result` |
| `/api/shell/agent/offline` | `agent:register` |
| `/api/shell/agent/job_update` | `agent:job_update` |

Agent tokens are bound to `client_id` and owner. Shared keys are isolated by the verified SHA-256 group; their requested owner is not an authorization input. Bootstrap is an explicit host-auth kind. Global visibility alone does not bypass managed-Runner ownership for dispatch. Query credentials and duplicate Authorization headers are rejected. Credential-verifier errors are never reflected in responses.

Registration requires generation 2 and all 22 original baseline capability bits. These bits are facts reported by a real executor, not defaults inferred from the generation. A partial DSH executor cannot register merely by supporting the six migrated direct request codecs. Same-instance reconnect preserves queued and dispatched work. A new instance retires the prior instance, settles prior requests with their dispatch evidence, and never transfers those requests to the replacement. The original bounded retirement history is 16 instances.

## Managed database agent-token authentication

`NewAgentTokenAuthenticator(repository, resolveHostUser, options)` returns the existing `Authenticate` callback accepted by `NewHTTPHandler`. It reads managed credentials through `AgentCredentialRepository.GetByHash`, resolves the existing host User by immutable positive ID on every call, and updates the original credential's `last_used_at` on a best-effort basis. It mounts no application route, connects to no database, starts no worker and caches no authentication result. Supply concurrency-safe dependencies and an explicit clock and positive `MaxTokenBytes`.

The repository returns an owned `AgentCredentialRecord` snapshot. This is the authentication projection of the original `api_keys` columns: `id`, `user_id`, `key_hash`, `kind`, `scopes`, `allowed_client_id`, `expires_at`, `revoked_at`. Lifecycle metadata (`name`, `key_prefix`, `created_at`, `last_used_at`) is retained by the native repository described in [managed credential storage](CREDENTIAL_STORAGE.md); the verifier does not replace that record or the key lifecycle. `UserID` remains a string reference, normalized at the repository/import boundary to the canonical host subject returned by `HostUserOwner`. The verifier strictly parses its positive int64 ID and rejects unconverted legacy IDs, profile names, leading zeros and other noncanonical representations. Original nullable Unix-second expiry/revocation values remain nullable integers. A returned row must match the computed lowercase SHA-256 hash and have no revocation marker. Raw database `kind="agent"` requires a valid client binding and maps to `Principal.Kind="agent_token"`. Original `user` and legacy empty kinds undergo the same credential/user/expiry checks but map to non-transport `api_token`, preserving the registry's 403. Unknown kinds are rejected and never upgraded to agents. All stored scopes are projected; exact requested-scope authorization belongs to the registry.

`HostUserOwner(id)` defines the new-record owner representation as `sub2api_user_` followed by the positive host ID in base-10 (no leading zeros). The maximum positive int64 produces a 32-character owner, within the original 64-character lowercase ASCII username alphabet. This helper is available to trusted dispatchers as well as authentication; changing its encoding requires migrating stored owners. `HostUserResolver` receives only that ID and must return the same ID with `Active=true` only if the current host user exists, is not deleted and has active status. It must not select a user by profile username or authorize from a stale snapshot. Nickname, role and model billing group are not inputs. An admin profile still produces an ordinary agent principal, with no bootstrap or group bypass.

This deterministic representation applies to **new records**, as permitted by `SUB2API_DSH_SYSTEM_ARCHITECTURE.zh-CN.md:173`. Existing WebCodex imports require an explicit old-user-ID to host-user-ID mapping and consistent owner/subject/authority-reference rewrites before admission. The verifier performs neither import nor rewriting and does not promise compatibility with an old client still submitting its original username as owner. New registrations may omit owner, allowing the registry to fill the verified value, or supply exactly `HostUserOwner(id)`. Username similarity never selects or merges users. Host User IDs must remain immutable and must not be reassigned to another person.

Managed records cannot carry `ProjectGrantID` or `SharedKeyHash`. Original `ProjectAgentTokenVerifier` is a separate configuration-backed verifier and is not implemented here; a project agent credential must never be represented as a managed database row. OAuth, shared keys, account credentials, bootstrap and open mode are outside this constructor. Original user/empty kinds are recognized only as verified non-transport identities, not as Runner agents. There is no verifier-chain fallback or auth-disabled mode. All stored scopes survive projection, including the original `agent:job_update`, future/unknown scopes and `admin`; scope order and duplicates are preserved. The verifier does not repeat issuance-time scope validation. Neither extra scopes nor `admin` turn a principal into bootstrap, satisfy a missing exact transport scope or bypass owner/client checks. The `job_update` path now consumes that exact scope; it does not grant host dispatch authority. Empty scopes authenticate but grant no transport operation.

### Source contracts and deliberate host boundaries

All WebCodex references below refer to frozen revision `97ad66949a859174911c2f6da2ff1063be98bfa9`.

| Contract | Original source and implementation boundary |
|---|---|
| Exact token bytes and hash | `src/auth/pat.rs:18-31`: SHA-256 of UTF-8 bytes, lowercase hex, no trim. The DB verifier at `src/auth/tokens.rs:76-79` looks up by hash rather than trusting the prefix. This implementation accepts valid UTF-8 within the explicit host byte limit. The generated `wc_agent_` plus 64-hex format (`pat.rs:47-59`) is not a universal DB-verification length requirement. `MaxTokenBytes` is a configured operational bound, not an invented source protocol constant. |
| Not found and errors | `crates/webcodex-store/src/accounts.rs:49-60` returns no row for missing/revoked hashes. `src/auth/tokens.rs:79` originally uses `if let Ok(Some(...))`, so an API-key query error can fall through to account lookup; the chain at `tokens.rs:352-379` distinguishes unrecognized from invalid credentials. This managed api_keys verifier fails closed on every repository/resolver error, with a fixed unavailable error and no fallback. It never wraps sensitive dependency error text. `(nil, nil)` means not found; invalid credentials and unknown kinds return a fixed invalid error. The existing HTTP handler returns its generic 401 for either error. Verified original `user`/empty kinds instead reach the registry as non-transport `api_token` and receive 403; this does not add PAT management or other credential verifier families. |
| Revocation and expiry | `accounts.rs:54` excludes every non-null `revoked_at`; `models.rs:295-302` considers any marker revoked and expiry reached at `now >= expires_at`, in Unix seconds. No future-dated revocation marker is ignored. The clock is read after host resolution; no balance, subscription or quota check substitutes for expiry. |
| Kind and scopes | `models.rs:305-316` defaults empty kind to `user`, and only raw `agent` is an agent. `src/auth/tokens.rs:99-113` classifies the verified row and projects `scopes_vec`; `models.rs:290-292` splits stored whitespace without deduplicating, despite its comment. `src/auth/scopes.rs:43-62` and the four `AGENT_SCOPES` at `crates/webcodex-core/src/authority.rs:102-107` constrain issuance, not per-request verification. Every stored scope is retained here, including future/unknown strings and `admin`. Registry requires the exact operation scope and the proper principal kind; extra values cannot broaden that authority. Go `strings.Fields` preserves the source whitespace behavior: U+0085 separates scopes; U+FEFF stays inside the scope string and cannot make that string match a known scope. |
| Client and owner bounds | `src/auth/pat.rs:147-167` admits normalized client IDs of 1-80 ASCII letters/digits/`-_.`; malformed stored values are rejected, not trimmed into another binding. `pat.rs:170-193` defines the 1-64 lowercase ASCII letters/digits/`_-` owner alphabet. The resolver uses immutable host ID; the existing registry enforces the exact owner/client equality. |
| Parent authority and project grants | `src/auth/project_credential.rs:19-24,84-96` defines the separate project agent verifier. OAuth checks include non-revoked owning client (`src/auth/tokens.rs:229-238`), project grant ownership (`tokens.rs:301-323`) and the currently active project-share subject/session (`src/auth/project_share.rs:50-63`). These are distinct from a managed api_keys row. No grant/ancestor validation is claimed here: project-derived credentials are outside the repository contract and cannot be projected into a grant group. |
| User and last-used | `src/auth/tokens.rs:80-114` checks the owning user, then expiry, and treats `last_used_at` failure as best effort. The host resolver must enforce active/not-deleted against the requested ID. Cancellation before or during dependencies returns no principal, including cancellation during the last-used write. Dependency calls use the request context; their implementations must honor deadlines. No private error is logged and no retry goroutine is started. |

The repository and user resolver remain trusted host adapters: they must return authoritative snapshots, apply explicit import mapping and exclude project-derived records. This package cannot make independently queried data transactionally atomic against a concurrent revoke, or stop a call in a dependency that ignores its context. It revalidates on every request and retains no positive authorization cache; in-flight work remains subject to the existing registry's dispatch-evidence rules. This feature neither cancels already-dispatched work nor implements a revocation broadcast.

The opt-in application integration is implemented by `server.ProvideWebCodexRunner`: `webcodex_runner.enabled` defaults to false, disabled configuration constructs no registry or credential dependency, and enabled configuration mounts the five original Runner transport paths during router assembly. The application passes the same runtime to `ProvideRouter` and `ProvideHTTPServer`; shutdown closes the in-memory registry. Preserve the original root `/api/shell/agent/...` paths rather than `/api/v1`, and keep model APIKey middleware out of the Runner credential path. Global host middleware, including CORS handling for `OPTIONS`, may run before the Runner handler.

The exact configuration keys are listed below. Enabling requires all six bounds to be supplied explicitly; their zero defaults are invalid when enabled, not operational recommendations. Environment variables use the shown names.

| `webcodex_runner.max_pending_per_runner` | `WEBCODEX_RUNNER_MAX_PENDING_PER_RUNNER` | `0`; require a positive integer for pending requests, including undelivered stop controls |

Allowed-origin CORS preflight can return 204 whether Runner is enabled or disabled. This does not authenticate a request or create a route: a subsequent unauthenticated POST returns 401 when enabled and 404 when disabled.

## Managed Runner credential lifecycle

When `webcodex_runner.enabled=true`, the host also mounts the original POST `/api/agent-tokens/{create,register_hash,list,revoke}` routes under actual panel JWT authentication, backend-mode guard, the shared per-user panel rate limiter and management audit. Current host admin/self authorization uses immutable ID; request `username` and response owner fields carry canonical `sub2api_user_<id>`, never mutable profile usernames. Runner tokens, model API keys and non-JWT admin credentials cannot manage tokens. The original `account:manage` surface is mapped to the host's full panel account authority for this slice; scoped WebCodex PAT/account/OAuth/bootstrap authentication remains separate and unavailable.

Create returns `wc_agent_` plaintext once after a hash-only INSERT. Hash registration never accepts plaintext. Lists/revokes select safe metadata only; revocation is an atomic user-and-kind-scoped UPDATE with the original first timestamp. Management bodies reuse the explicitly configured `webcodex_runner.max_body_bytes`, and list size remains 200. All four management request bodies are entirely omitted from audit, while the one-time response and policy errors use `Cache-Control: no-store`. Original request/response fields, scope/null defaults, validation, error/status behavior, collision and retry limits, current user checks, and the unimplemented cross-family account-credential hash check are specified in [managed credential storage](CREDENTIAL_STORAGE.md#host-authorized-management-routes). This slice creates no UI or model tool and adds no Job authority beyond retaining the original scope value.

## Synchronous requests and lifecycle

Trusted host callers use `Enqueue` only after establishing the original project and operation scopes. The HTTP adapter has no dispatch endpoint. The caller supplies the durable unique `request_id`; this memory registry does not replace the Connector execution record or idempotency transaction.

The synchronous dispatch decoder accepts `run_shell`, `run_process`, `run_script`, `file_read`, `file_write` and `file_list`. Each request must match the target's advertised capability. Job-backed operations and deferred families fail explicitly. Structured argv/script payloads remain structured and are not concatenated into shell commands. A request is delivered at most once while pending, including after a polling response is lost. Consuming a result requires its exact dispatched request, client and active instance. A duplicate consumed/expired result receives the original HTTP 400 failure behavior; success means an in-memory waiter accepted it, not a durable acknowledgement.

Each returned `Pending` must be awaited with a bounded context or explicitly cancelled. Cancellation before dispatch removes the queue item. After dispatch, `Outcome.Dispatched` stays true even when the waiter fails, so timeout, disconnect and replacement cannot prove that execution never started. Cancellation does not stop a remote process and cannot authorize automatic retry. `Close` synchronously settles all waiters and cancels owned recovery deadline timers; the registry owns no subprocesses or sockets.

Runner views preserve `online`/`stale`, second-based timestamps, and `pending_requests` as the undelivered queue length. Result stdout/stderr preserve the original last-256-KiB UTF-8 tail and truncation notice. The notice is additional to the per-stream limit; the complete HTTP body has a separate configured bound. Registry options bound retained nodes and pending requests. Original shared-key per-group/global ceilings remain 16/1024. Cancelled queue items are removed immediately. Offline records are retained until registry disposal; TTL collection is deferred.

## Legacy structured process Jobs

Trusted host code can call `StartProcessJob(Access, protocol.JobInvocation)` for the original `JobProcessOperation`, followed by `GetJob`, `ListJobs`, `JobLog` and `StopJob`. The caller must first authorize the project and original operation scope, establish truthful project/session context, and supply durable unique `job_id` and `request_id` values. These APIs expose no HTTP user-dispatch route and do not establish Connector idempotency or durable receipt. Arguments stay typed; caller previews are replaced by the source's bounded, redacted `process_preview`. Validation plans, SSH, detached jobs, scripts and Codex Jobs remain outside this slice.

The registry stores Jobs and the original request-to-Job binding independently from synchronous requests. Poll moves the start request's dispatch evidence to its Job and releases its queue storage, retaining the binding until terminal completion. A Job has no `Pending.Wait`; `/result` cannot settle it. The original `POST /api/shell/agent/job_update` uses the real managed verifier and exact `agent:job_update` scope, then checks client, captured owner/group, active instance, Job lease and optional original request ID. A body that supplies a different request ID is rejected. This adaptation additionally refuses updates before the start request was actually polled and rejects mismatches before refreshing registry liveness. The verifier may still touch the credential's best-effort `last_used_at` before registry authorization.

`queued` means initially queued on this Server. Poll projects `agent_queued` without claiming a child process started. Running/terminal updates apply the original structured execution state and bounded activity rules; a validation/activity/command-state protocol violation latches `failed` with the source violation code, rather than reporting successful execution. The first accepted terminal lifecycle, result, logs and terminal observation timestamp never change on later updates. Explicit offline and stale dispatched legacy Jobs become `lost`; reconciliation-capable Jobs follow the recovery rules below. Replacement never transfers process Jobs, and same-instance registration never revives a terminal Job. Restart reconstruction is not implemented.

Stopping a never-polled Job removes its local request and returns `stopped`/`not_started`. Stopping a dispatched Job registers `stop_job` once and returns `stop_requested`; delivery is not proof that a remote process stopped. Explicit dispatch and stop-registration facts prevent a later legacy `queued`/`started` update from authorizing a local-only stop or replaying the control. This deliberately closes the frozen source's lifecycle-string-only stop gap. Stale dispatched legacy `queued`/`started` records are also eligible for local `lost` observation. A terminal update removes queued stop controls; `Close` only clears local records and never claims remote termination.

`JobLog` implements an immediate explicit cursor read. Stdout and stderr have independent one-based absolute cursors, retained lower bounds and truncation flags. Each append stream retains at most 256 KiB, dropping whole lines first and preserving UTF-8. `tail_lines > 0` takes precedence over supplied cursors, as in the source. Legacy `stdout_tail`/`stderr_tail` replacement resets the corresponding cursor to a new baseline and can move it backwards; it is not an authoritative snapshot. Transport truncation markers retain their original behavior. Only cursor-less source `wjob1` observation tokens are exposed here; cursor-aware automatic deltas and waiters are not implemented.

**Sequenced reconciliation is opt-in.** With an explicit positive `webcodex_runner.job_recovery_grace_seconds` / `WEBCODEX_RUNNER_JOB_RECOVERY_GRACE_SECONDS` (library `Options.JobRecoveryGrace`), registration may advertise `job_state_reconciliation=true`. Zero is the default and refuses this capability; negative or nonrepresentable duration values are invalid. All 22 generation-2 baseline bits remain mandatory. Same-instance capability downgrade is rejected. The existing `register` and `job_update` routes reuse protocol-owned inventory/snapshot DTOs.

Registration requires `active_complete=true`, active entries before terminal history, unique Job/request IDs, at most 64 active and 64 terminal records, and at most 1 MiB for the complete typed inventory serialized as original Rust JSON, including metadata. HTML characters and U+2028/U+2029 count as their literal UTF-8 bytes; literal backslash sequences remain escaped. These are Runner inventory bounds, not Server Job capacity. Each snapshot stream is at most 64 KiB, with positive first line, saturating next-line arithmetic matching Rust `str::lines`, and `truncated=true` whenever earlier lines are omitted. Applying a newer snapshot may not regress either absolute next-line cursor.

The registry validates every inventory entry before any lease, liveness, pending count or Job mutation. Under one registry mutex it checks existing registration ownership/group, retired instances, captured Job client/instance/owner/group, dispatched request binding, full recovery context, timestamps, structured process metadata, activity and lifecycle consistency; it then commits registration and reconciliation together. Inventory is transient and never retained as a second Job mirror. Original Server creation time is preserved, while validated started/ended times come from the snapshot. Missing active Jobs become `lost`; unpolled queued Jobs remain queued. Retained terminal Jobs never revive. Stale sequences are ignored; an equal inventory sequence applies only during recovery. Register acknowledgements and concurrent updates cannot roll back a higher sequence or a terminal record.

Sequenced updates require positive uint64 `update_seq`, a canonical Runner-owned active or terminal status without whitespace, `finished` exactly matching terminal state, no active exit/duration fields and `completed` with exit code zero. Sequence values at or below the accepted sequence are idempotent; the first terminal result/logs stay immutable. `log_snapshot` is mutually exclusive with all chunk/tail fields. Snapshot shape is checked before replay handling and absolute cursors before application. Structured lifecycle/activity/progress violations use the original failed-Job protocol-violation outcome; unknown validation, SSH and workflow execution families are not accepted by this process-only slice. Sequenced process dispatch also checks that its context can be reconciled before queue mutation.

Explicit offline or observed stale transport begins same-instance recovery for dispatched Jobs. The deadline starts at this Server's first recovery observation and does not reset on heartbeat or repeated offline. One cancellable deadline timer per recovering Job enforces expiry without another Job query; capacity bounds these timers, and terminalization, successful reconciliation and `Close` cancel them. A late valid snapshot cannot escape an elapsed deadline by winning the mutex before the timer callback. During recovery only authoritative inventory or a higher-sequence snapshot update may restore state; stop is refused until recovery resolves. Authoritative running snapshots permit a fresh stop after a prior stop control was dropped or delivered. Undispatched Jobs become `lost` on explicit offline, and new-instance replacement terminates prior active Jobs. Request-to-Job IDs remain reserved until terminal completion as an explicit native binding, independently of pending queue capacity.

While a Runner-owned active lifecycle is recovering, `GetJob`, `ListJobs` (including its status filter) and the Job view in `JobLog` report `status="recovering"`. The internal lifecycle retains the original Runner status; `recovering` is never accepted as a Runner update state. Authoritative reconciliation restores the public status to the reconciled lifecycle. A terminal lifecycle remains visible even if older recovery metadata is retained.

This supports only known process Jobs admitted by the same running Server and owned by the same Runner instance. Unknown or already-collected Job inventory, Server restart reconstruction, workflow/validation/SSH inventory, and cross-instance detached transfer are explicitly refused: the native durable authority/projection dependencies have not been migrated. An empty new-instance inventory can replace a lease but cannot adopt prior Jobs. No `recovered_after_server_restart` claim is made. The 900-second terminal TTL starts at the Server's first terminal observation, never Runner `ended_at`.

With capability false, every inventory and `log_snapshot` stays refused. Optional legacy `update_seq` is recorded (including zero or decreasing values), not a replay key; status whitespace, legacy finished fallback, completed-without-zero behavior and tail cursor resets remain unchanged.

`Options.MaxJobsPerRunner` explicitly bounds all retained active and terminal Jobs; zero disables Job dispatch for direct library callers and negatives are invalid. Enabling the application requires an explicit positive `webcodex_runner.max_jobs_per_runner` (or `WEBCODEX_RUNNER_MAX_JOBS_PER_RUNNER`), independently from `max_pending_per_runner`. The host passes each configured value only to its matching registry option; neither budget defaults or falls back to the other. Capacity is enforced per Runner, and reaching it never evicts an active Job. A polled start no longer occupies pending capacity, allowing stop controls even when the active Job budget is full. Undelivered stop controls consume pending capacity; rejection leaves Job state and stop-registration evidence unchanged. The source's 15-minute terminal retention is measured from the Server's first terminal observation, never Runner timestamps. Job APIs lazily collect expired terminal records and bindings, including before admitting a new Job; terminal retention has no background timer. Recovery deadlines use the separate owned timers described above. At most `MaxRunners * MaxJobsPerRunner` Job records are retained alongside the independently bounded registry. Runner registration TTL collection remains deferred.

Source behavior and limits are from frozen revision `97ad66949a859174911c2f6da2ff1063be98bfa9`: registry `job_updates.rs:426-532,1416-1490,1777-2162`, `jobs.rs:200-270,308-455,615-658`, `polling.rs:569-603`, `reconciliation.rs:756-834`, core `runner_protocol.rs:485`, `audit_preview.rs:22-87`, `sensitive_text.rs:4-27`, and `src/runner_http/handlers.rs:385-454`. The per-Job deployment budget and dispatch-evidence safeguards are native host adaptations, not invented source constants.

## Validation

Run from the backend directory:

```sh
go test -race ./internal/webcodex/...
DSH_RUNNER_CHECKOUT=/absolute/path/to/deepseek-harness go test -run TestDSH -v ./internal/webcodex/runner
```

Focused credential coverage uses only memory fixtures:

```sh
GOPROXY=off GOSUMDB=off GOTOOLCHAIN=local CGO_ENABLED=1 \
  go test -race -count=1 -run '^TestAgentCredential' ./internal/webcodex/runner
```

The full local runner/protocol race suite also exercises the existing loopback fixtures and needs no external service. The `TestAgentCredential*` tests cover the public SHA-256 vector/exact bytes, explicit dependencies and byte bounds, malformed rows/kinds, canonical string user references, source client limits, complete stored scope projection and whitespace, expiry equality, active same-ID host user, profile-independent owner, sanitized lookup errors, best-effort touch, cancellation and concurrent fresh checks. Memory-only HTTP tests use the real verifier with fake repositories and fabricated results to cover the four polling routes, revocation/deletion/user disable after registration, exact scope/client/owner rejection without lease or pending-result mutation, user/legacy-kind transport 403, mixed known/future scopes, admin without bootstrap, body/header credential boundaries and unchanged G2 admission. No test token is a deployed credential. These tests do not validate a real repository, migration, executor or application route mount.

The opt-in cross-language tests launch the test-only DSH stdin driver through `node --import tsx/esm`. They need DSH's workspace dependencies. They round-trip direct request JSON, including signed/unsigned 64-bit extrema, and prove that the actual partial DSH client is rejected by the Go generation check before executor invocation. Go loopback tests use a fixture credential verifier and fabricated results; they do not prove local execution or end-to-end ChatGPT Connector operation.

## Migration limitations

The native managed-credential verifier now has a host SQL credential repository, embedded migration and current User repository adapter; see [storage integration](CREDENTIAL_STORAGE.md) for the original field map and offline SQL fixture checks. The five polling transport routes have default-off router/DI mounting; enabling them does not add business dispatch or persistent registry/results. WebSocket/QUIC, provider policy sanitization, paged project inventories, durable/restart Job recovery, Generic ToolRuntime, ProjectConnector/OAuth/MCP and UI are not implemented here. Registration carrying policy/provider inventory or unknown Job recovery inventory is explicitly rejected until those owned semantics are migrated. A database, transaction and outbox are required before claiming persistent result receipt, restart recovery or durable idempotency. A full generation-2 DSH execution provider with its real non-Agent guard/approval/filesystem/sandbox owner remains required. No package option disables that generation check.
